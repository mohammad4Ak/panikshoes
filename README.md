# Panikshoes — فروشگاه کفش پانیک

فروشگاه آنلاین کفش با رابط فارسی و راست‌به‌چپ، طراحی اسپرت با گوشه‌های نرم، نمایش واکنش‌گرا و پنل مدیریت. پروژه با Next.js App Router ساخته شده و داده‌های کاربران، محصولات و سفارش‌ها را در PostgreSQL نگه می‌دارد.

ثبت سفارش، مدیریت ارسال، پرداخت کارت‌به‌کارت با بررسی ادمین و گزارش فروش پیاده‌سازی شده‌اند. **اتصال واقعی به زرین‌پال هنوز تکمیل نشده است**؛ ثبت سفارش یا ارسال رسید به معنی پرداخت موفق نیست.

## امکانات

- ویترین و جست‌وجوی محصولات، فیلتر دسته‌بندی، قیمت و موجودی، مرتب‌سازی و صفحهٔ جزئیات با انتخاب سایز و رنگ.
- مشخصات مرتب و قابل ویرایش کفش، امتیازدهی ۱ تا ۵ و نظرات کاربران با تأیید ادمین، برچسب خریدار و مرتب‌سازی محبوب‌ترین و پربازدیدترین.
- آمار بازدید روزانه، کل بازدید، بازدیدکنندگان تقریبی، صفحات و محصولات پربازدید و گزارش IP مخصوص ادمین.
- سبد خرید ماندگار در مرورگر و تسویه‌حساب با نام گیرنده، آدرس، شمارهٔ تماس و انتخاب روش ارسال.
- ثبت‌نام و ورود با ایمیل و رمز عبور، ویرایش مشخصات، تغییر رمز، مدیریت آدرس‌های ذخیره‌شده و مشاهدهٔ سفارش‌های خود.
- پنل ادمین برای مدیریت محصولات، دسته‌بندی‌ها، تصاویر، کاربران، وضعیت سفارش‌ها و روش‌های ارسال.
- تنظیمات عمومی برای برندینگ و لوگو، رنگ‌بندی سبز یا عسلی، محصولات اسلایدر صفحهٔ اول و زمان چرخش، بنر، اطلاعیه، تماس و شبکه‌های اجتماعی و عنوان و توضیح سایت.
- مدیریت روش‌های پرداخت، کارت مقصد و صف بررسی رسیدها؛ صفحهٔ کارت‌به‌کارت با مهلت ۱۰ دقیقه‌ای، رزرو موجودی و پیگیری واریز دیرهنگام.
- داشبورد فروش، دفتر سفارش‌ها، فیلتر پرداخت و وضعیت سفارش و خروجی CSV قابل باز شدن در Excel.
- صدور فاکتور فارسی PDF پس از تأیید سفارش توسط ادمین و دریافت آن از جزئیات سفارش مشتری و ادمین.
- صفحهٔ نتیجهٔ پرداخت با حالت‌های موفق، ناموفق، در انتظار و وضعیت نامشخص، بر اساس دادهٔ سفارش متعلق به کاربر.
- آیکون‌های SVG اختصاصی و حرکت‌های ملایم هنگام ورود عناصر و تعامل؛ پشتیبانی از تنظیم کاهش حرکت مرورگر.

## فناوری‌ها

## اجرای محلی

پیش‌نیازها: **Node.js 20.9 یا بالاتر**، npm و یک دیتابیس PostgreSQL در دسترس. دیتابیس می‌تواند روی دستگاه، داخل Docker یا روی یک سرویس ابری باشد؛ پروژه خودش PostgreSQL را اجرا نمی‌کند.

```bash
git clone https://github.com/mohammad4Ak/panikshoes.git
cd panikshoes
cp .env.example .env
npm ci
```

در PowerShell می‌توان به جای دستور کپی بالا از `Copy-Item .env.example .env` استفاده کرد. سپس فایل `.env` را با مشخصات دیتابیس خود تنظیم کنید. نمونهٔ اتصال برای دیتابیس محلی `shoes_shop`:

```dotenv
DATABASE_URL="postgresql://postgres:YOUR_DATABASE_PASSWORD@localhost:5432/shoes_shop?schema=public"
AUTH_SECRET="YOUR_RANDOM_SECRET"
```

برای ساخت مقدار تصادفی `AUTH_SECRET`:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
```

دیتابیس را از قبل ایجاد کنید و مایگریشن‌های موجود را روی همان دیتابیس اعمال کنید:

```bash
npm run db:deploy
npm run dev
```

سایت در [localhost:3000](http://localhost:3000) باز می‌شود. `npm ci` به‌صورت خودکار Prisma Client را تولید می‌کند. پس از تغییر schema نیز می‌توان `npx prisma generate` را اجرا کرد.

### اجرا در شبکهٔ محلی

برای دسترسی از گوشی یا دستگاه دیگری که به همان شبکه متصل است:

```bash
npm run dev:lan
```

آدرس IPv4 اتصال وای‌فای کامپیوتر را با `ipconfig` پیدا کنید و در مرورگر گوشی `http://<IP>:3000` را باز کنید. نام میزبان یا IP شبکه را در `allowedDevOrigins` فایل `next.config.js` نیز وارد کنید؛ در صورت تغییر IP، این تنظیم باید به‌روز شود. سرور و کامپیوتر باید روشن بمانند.

### دادهٔ نمونه و حساب ادمین

برای یک دیتابیس آزمایشی، ساخت حساب‌ها، دسته‌بندی‌ها و محصولات نمونه اختیاری است:

```bash
npm run db:seed
```

| نقش | ایمیل | رمز نمونه |
| --- | --- | --- |
| ادمین | `admin@shoeland.ir` | `admin123` |
| مشتری | `user@test.com` | `user123` |

Seed اصلی داده‌های موجود را به‌روزرسانی نمی‌کند و رکوردهای نمونهٔ مفقود را می‌سازد. حساب‌های بالا فقط برای آزمایش هستند؛ آن‌ها را با این رمزها در محیط عمومی استفاده نکنید. ورود ادمین از `/login` انجام می‌شود و پنل در `/admin` قرار دارد.

برای سفارش‌های نمونهٔ داشبورد، پس از Seed اصلی و فقط در دیتابیس آزمایشی:

```bash
npm run db:seed:orders
```

این دستور در هر اجرا سفارش‌های جدید اضافه می‌کند.

### تنظیم ارسال پیش از ثبت سفارش

مایگریشن‌ها چهار روش **پست پیشتاز، پست معمولی، تیپاکس و ماهکس** را به‌صورت غیرفعال ایجاد می‌کنند. از `/admin/shipping` هزینه‌ها را تنظیم و حداقل یک روش را فعال کنید تا مشتری بتواند سفارش ثبت کند. ادمین می‌تواند روش‌ها را اضافه، ویرایش، حذف، غیرفعال و مرتب کند.

تمام مبالغ به **تومان** هستند:

```text
هزینهٔ ارسال = مبلغ پایه + هزینهٔ هر جفت اضافه × (تعداد کل جفت‌ها − ۱)
```

اگر جمع قیمت کالاها به حد ارسال رایگان روش انتخاب‌شده برسد، هزینه صفر می‌شود. حد خالی یعنی بدون شرط ارسال رایگان و حد صفر یعنی ارسال همواره رایگان. نام روش و هزینهٔ آن در سفارش ذخیره می‌شوند؛ تغییر تعرفه یا حذف روش، این سابقه را عوض نمی‌کند.

## سفارش‌ها و نشست کاربر

قیمت، موجودی، سایز، رنگ و هزینهٔ ارسال در سرور بررسی می‌شوند. تغییر قیمت یا تعرفه هنگام تسویه‌حساب نیاز به بازبینی مشتری دارد. درخواست تکراری با شناسهٔ همان ثبت سفارش، سفارش دیگری نمی‌سازد.

موجودی هنگام ثبت سفارش کسر می‌شود. لغو سفارش مجاز، موجودی را برمی‌گرداند؛ بازگشایی سفارش لغوشده موجودی را دوباره بررسی و کسر می‌کند. سفارش کارت‌به‌کارت پرداخت‌نشده فقط از مسیر بررسی پرداخت می‌تواند وارد پردازش شود. وضعیت‌های ارسال‌شده و تحویل‌شده محدودیت تغییر دارند و سابقهٔ سفارش‌های دارای رسید، پرداخت‌شده یا ارسال‌شده با حذف از بین نمی‌رود.

نشست مشتری و ادمین پس از **۳۰ دقیقه بی‌فعالیتی** منقضی می‌شود. تعامل واقعی مانند کلیک، تایپ، حرکت اشاره‌گر و اسکرول نشست معتبر را تمدید می‌کند؛ باز بودن تب و بررسی خودکار نشست آن را تمدید نمی‌کنند. تب‌های یک مرورگر هماهنگ هستند و محدودیت در سرور نیز اعمال می‌شود. پایان نشست، سبد خرید و اطلاعات تایپ‌شدهٔ فرم تسویه‌حساب را پاک نمی‌کند.

## تنظیمات عمومی فروشگاه

بخش `/admin/settings` نام و شعار برند، لوگوی اصلی و نسخهٔ روشن اختیاری برای زمینهٔ تیره، اطلاعیهٔ قابل فعال‌سازی با لینک اختیاری، شماره تماس، ایمیل، نشانی، ساعات پاسخ‌گویی، اینستاگرام و تلگرام، عنوان سایت و توضیح آن را مدیریت می‌کند. تغییرات و تصاویر ابتدا در فرم پیش‌نمایش داده می‌شوند و با «ذخیره تنظیمات» در سایت اعمال می‌شوند. حذف لوگوی سفارشی، لوگوی فعلی فروشگاه را برمی‌گرداند؛ فیلدهای تماسِ خالی در سایت نمایش داده نمی‌شوند.

لوگو از آپلود تصویر فعلی با فرمت PNG، JPG، WebP یا GIF و سقف ۵ مگابایت استفاده می‌کند. متن اطلاعیه متن ساده است و HTML اجرا نمی‌شود. اطلاعیهٔ غیرفعال فقط در پنل ادمین باقی می‌ماند. لینک‌های اطلاعیه و شبکه‌های اجتماعی اعتبارسنجی می‌شوند. برای تغییر هم‌زمان تنظیمات، نسخهٔ رکورد بررسی می‌شود؛ ادمین دوم باید نسخهٔ تازه را دریافت و تغییرات نگه‌داشته‌شدهٔ خود را بازبینی کند.

تنظیمات در رکورد واحد دیتابیس نگه‌داری می‌شوند و روی سربرگ، فوتر، صفحات برند و تماس و عنوان مرورگر اعمال می‌شوند. پس از ذخیره، کش layout باطل می‌شود و مرورگر فروشگاه هنگام جابه‌جایی صفحه یا بازگشت به پنجره، تنظیمات عمومی تازه را دریافت می‌کند. نام فروشنده هنگام صدور فاکتور ثبت می‌شود و فاکتورهای قبلی با تغییر برند دوباره نوشته نمی‌شوند.

### زیرمنوی تنظیمات عمومی

تنظیمات عمومی به شش بخش برندینگ و لوگو، رنگ‌بندی، صفحهٔ اول، اطلاعیه، اطلاعات تماس و عنوان/توضیحات سایت تقسیم شده است. در دسکتاپ از منوی بازشونده و در موبایل از نوار زیرمنو استفاده می‌شود. هر بخش لینک مستقیم دارد (مثلاً `/admin/settings#appearance`) و جابه‌جایی بین آن‌ها پیش‌نویس را حفظ می‌کند. «ذخیره تنظیمات» تغییرات تمام بخش‌ها را یکجا ذخیره می‌کند.

### رنگ‌بندی سایت

در «تنظیمات عمومی ← رنگ‌بندی» می‌توان بین رنگ‌بندی سبز و ترکیب عسلی، کرم و قهوه‌ای گرم انتخاب کرد. انتخاب تا زدن دکمهٔ ذخیره پیش‌نویس است و پس از ذخیره روی فروشگاه و پنل مدیریت اعمال می‌شود. پیش‌فرض سبز است؛ هر زمان می‌توان به آن برگشت. رنگ وضعیت‌های پرداخت و خطا مستقل از رنگ‌بندی برند باقی می‌ماند.

## صفحهٔ اول

از مسیر «تنظیمات عمومی ← صفحهٔ اول» می‌توان حداکثر ۱۰ محصول را برای بخش اصلی بالای صفحه انتخاب، حذف و مرتب کرد و زمان تعویض را بین ۵ تا ۱۲۰ ثانیه تنظیم کرد (پیش‌فرض ۱۰ ثانیه). عکس اول هر محصول همراه نام و لینک همان محصول نمایش داده می‌شود؛ انتخاب محصول ناموجود برای معرفی مجاز است و موجودی یا امکان خرید را تغییر نمی‌دهد. بدون انتخاب محصول، ویترین اصلی از انتخاب خودکار قبلی استفاده می‌کند. محصولات حذف‌شده یا بدون عکس اصلی در نمایش کنار گذاشته می‌شوند و اگر هیچ انتخاب معتبری نماند، حالت خودکار فعال می‌شود.

دو فلش در طرفین عکس برای نمایش محصول قبلی و بعدی قرار دارند؛ کنترل با کلیدهای جهت، Home و End نیز هنگام تمرکز روی فلش‌ها پشتیبانی می‌شود. چرخش خودکار هنگام تمرکز صفحه‌کلید، قرارگرفتن نشانگر روی اسلایدر یا پنهان‌شدن تب متوقف می‌شود. ترجیح کاهش حرکت مرورگر رعایت می‌شود. تنظیم این قسمت از بنر تصویری عریض پایین‌تر مستقل است و پس از «ذخیره تنظیمات» اعمال می‌شود. آزمون دیتابیس با `npm run test:home-hero:db` انجام می‌شود و همهٔ تغییرات آن rollback می‌شوند.

صفحهٔ اول یک بنر تصویری، راهنمای انتخاب کفش برای کاربردهای مختلف و اطلاعات خرید دارد. در بخش «صفحهٔ اول» از تنظیمات عمومی ادمین، نمایش بنر، عکس، متن و دکمهٔ آن قابل تغییر است؛ تغییرات فقط پس از ذخیره اعمال می‌شوند. تصویر پیش‌فرض از فایل public/brand/panik-trail-banner.png استفاده می‌کند و حذف عکس سفارشی آن را برمی‌گرداند. بنر خاموش در صفحهٔ اصلی نمایش داده نمی‌شود و محتوای آماده‌نشدهٔ آن در API عمومی منتشر نمی‌شود.

لینک‌های راهنمای انتخاب به دسته‌بندی‌های واقعی متصل‌اند. اطلاعات ارسال و پرداخت از روش‌های فعال و قابل استفادهٔ فروشگاه خوانده می‌شوند؛ هزینهٔ نهایی ارسال در تسویه‌حساب نمایش داده می‌شود. اطلاعات کارت بانکی در صفحهٔ اصلی منتشر نمی‌شود. تست بخش‌های جدید با npm run test:home اجرا می‌شود.

## فاکتور سفارش

برای سفارش کارت‌به‌کارت، تأیید واریز توسط ادمین در `/admin/payments`، تأیید پرداخت، تغییر وضعیت به «در حال پردازش» و صدور فاکتور را در یک تراکنش انجام می‌دهد. برای سفارش‌های قدیمی، تأیید وضعیت پردازش، ارسال یا تحویل همچنان فاکتور صادر می‌کند. جزئیات سفارش در `/profile` و `/admin/orders` دکمهٔ دریافت PDF دارند؛ دانلود مخصوص صاحب سفارش و ادمین است.

شماره و تاریخ صدور، نام محصولات هنگام خرید، سایز، رنگ، تعداد، قیمت‌های ثبت‌شده، مشخصات خریدار و گیرنده، روش و هزینهٔ ارسال و مجموع سفارش ذخیره می‌شوند. تغییر بعدی محصول یا حساب کاربری فاکتور صادرشده را عوض نمی‌کند و تغییر وضعیت دوباره، شمارهٔ تازه‌ای نمی‌سازد. پس از لغو، فاکتور با اعلام وضعیت لغو برای حفظ سابقه در دسترس می‌ماند؛ سفارش دارای فاکتور قابل حذف نیست.

مایگریشن فاکتور برای سفارش‌های قبلیِ در حال پردازش، ارسال‌شده و تحویل‌شده نیز فاکتور می‌سازد. تاریخ صدور آن‌ها زمان اجرای مایگریشن است و تاریخ ثبت سفارش جدا نمایش داده می‌شود. فاکتور نتیجهٔ تأیید سفارش توسط فروشگاه است و به معنی تأیید پرداخت نیست.

## گزارش فروش

داشبورد `/admin` فروش تأییدشده، مبلغ کالاها، هزینهٔ ارسال دریافتی، تعداد سفارش‌ها، کالاهای پرفروش و مقایسه با دورهٔ قبل را نمایش می‌دهد. بازه‌های ۷، ۳۰ و ۹۰ روزه، ماه شمسی جاری و بازهٔ دلخواه تا ۳۶۶ روز پشتیبانی می‌شوند.

سفارش‌های پرداخت‌نشده و لغوشده از فروش تأییدشده کنار گذاشته می‌شوند. سفارش لغوشده با پرداخت تأییدشده جدا نمایش داده می‌شود و به معنی استرداد وجه نیست. دفتر سفارش‌ها صفحه‌بندی و فیلتر دارد؛ خروجی **CSV سازگار با Excel** همهٔ ردیف‌های مطابق فیلتر را تا سقف ۱۰٬۰۰۰ سفارش شامل می‌شود. تاریخ‌ها بر مبنای منطقهٔ زمانی تهران و مبالغ به تومان هستند.

بازهٔ گزارش بر اساس **تاریخ ثبت سفارش** است. بهای خرید کالا، هزینه‌های فروشگاه، هزینهٔ واقعی حمل، تاریخ دریافت وجه و استرداد وجه در مدل فعلی ثبت نمی‌شوند؛ این بخش گزارش فروش است و سود واقعی یا جریان نقدی را محاسبه نمی‌کند.

## وضعیت پرداخت و محدودیت‌های فعلی

پیش از پذیرش سفارش، در `/admin/payment-methods` شمارهٔ کارت، نام صاحب حساب و بانک خود را ثبت و کارت‌به‌کارت را فعال کنید. روش‌ها ابتدا غیرفعال هستند و اطلاعات بانکی نمونه ندارند. زرین‌پال تا تکمیل اتصال واقعی قابل فعال‌سازی نیست. غیرفعال‌کردن روش یا ویرایش کارت، اطلاعات و امکان پیگیری سفارش‌های قبلی را تغییر نمی‌دهد.

تسویه‌حساب به `/payment/transfer/[id]` هدایت می‌شود. شماره و نام کارت مقصد، مبلغ تومان و معادل ریال و مهلت ذخیره‌شده در سرور نمایش داده می‌شوند. موجودی از لحظهٔ ثبت سفارش برای ۱۰ دقیقه رزرو است؛ رفرش صفحه مهلت را تمدید نمی‌کند. با دریافت رسید، مهلت متوقف و رزرو تا تصمیم ادمین حفظ می‌شود. بدون رسید، سفارش منقضی و موجودی دقیقاً یک بار آزاد می‌شود. سفارش‌های قدیمی بدون روش پرداخت جدید، خودکار منقضی نمی‌شوند.

کاربر می‌تواند پیش از ثبت رسیدِ منتظر بررسی، از صفحهٔ پرداخت «انصراف از خرید» را تأیید کند. سفارش در تاریخچه با وضعیت لغوشده باقی می‌ماند و موجودی همان لحظه، دقیقاً یک بار آزاد می‌شود. پرداخت تأییدشده یا رسید در انتظار بررسی، به رسیدگی ادمین نیاز دارد. اگر کاربر پیش از انصراف واریز کرده باشد، مسیر صریح ارسال رسید برای پیگیری همچنان در دسترس است. در خرید هم‌زمان آخرین کالا، کاربر ناموفق پیام عذرخواهی و کمبود موجودی دریافت می‌کند و سبد او برای بازبینی حفظ می‌شود.

تصاویر رسید PNG، JPEG و WebP تا ۵ مگابایت در دیتابیس به‌صورت خصوصی ذخیره می‌شوند؛ فقط صاحب سفارش و ادمین می‌توانند آن‌ها را ببینند. چهار رقم آخر کارت و شمارهٔ پیگیری برای تطبیق هستند؛ هیچ‌کدام و هیچ پارامتر URL یا تصویر رسیدی به‌تنهایی پرداخت را تأیید نمی‌کند. ادمین باید واریز واقعی به حساب را بررسی کند. تصمیم، علت رد، زمان و شناسهٔ بررسی‌کننده و سابقهٔ رسیدها نگهداری می‌شوند.

رد رسیدِ سفارش رزروشده، ۱۰ دقیقه فرصت اصلاح می‌دهد. مسیر «واریز کردم، مهلت تمام شد» رسید دیرهنگام را بدون رزرو مجدد می‌پذیرد؛ تأیید چنین پرداختی ابتدا موجودی را به‌صورت اتمی دوباره بررسی و رزرو می‌کند و در صورت کمبود، تصمیم نهایی نیاز به رسیدگی ادمین دارد. سفارش دارای پرداخت تأییدشده با لغو به معنی بازپرداخت وجه نیست.

در سرور دائمی Node، آزادسازی هر ۳۰ ثانیه بررسی می‌شود و هنگام خواندن کاتالوگ، سفارش‌ها و پرداخت نیز بررسی انجام می‌شود. در محیط serverless، زمان‌بند میزبان را برای درخواست هر دقیقه به `GET /api/cron/payments/expire` با هدر `Authorization: Bearer <CRON_SECRET>` تنظیم کنید؛ مقدار محرمانه باید حداقل ۳۲ نویسه باشد. بدون زمان‌بند، سفارش در اولین مراجعهٔ مرتبط پس از مهلت منقضی می‌شود. تایمر مرورگر مرجع تأیید یا انقضای پرداخت نیست.

برای بررسی ظاهر صفحهٔ نتیجه، فقط در حالت توسعه می‌توان از `/payment/result?preview=success`، `preview=failed` یا `preview=pending` استفاده کرد. این پیش‌نمایش‌ها دادهٔ واقعی را تغییر نمی‌دهند و در محیط production فعال نیستند.

موجودی فعلاً در سطح محصول نگهداری می‌شود و برای هر ترکیب سایز و رنگ موجودی جدا وجود ندارد. تأیید خودکار بانکی و بازپرداخت خودکار پیاده‌سازی نشده‌اند.

## متغیرهای محیطی

| متغیر | کاربرد |
| --- | --- |
| `DATABASE_URL` | آدرس اتصال PostgreSQL؛ الزامی |
| `AUTH_SECRET` | کلید تصادفی محرمانه برای نشست‌ها؛ الزامی |
| `BLOB_READ_WRITE_TOKEN` | اختیاری؛ با وجود آن، آپلود تصویر به Vercel Blob انجام می‌شود |
| `ZARINPAL_MERCHANT_ID` | برای اتصال آیندهٔ درگاه؛ فعلاً در جریان پرداخت استفاده نمی‌شود |
| `CRON_SECRET` | کلید محرمانهٔ حداقل ۳۲ نویسه برای زمان‌بند آزادسازی رزرو در محیط serverless |

فایل `.env` و اطلاعات واقعی اتصال یا کلیدها را منتشر نکنید. هنگام تغییر `AUTH_SECRET`، نشست‌های قبلی نیاز به ورود دوباره دارند.

## آپلود و استقرار

آپلود تصویر مخصوص ادمین است و JPG، PNG، WebP و GIF غیرخالی تا ۵ مگابایت را با بررسی امضای فایل می‌پذیرد. اگر `BLOB_READ_WRITE_TOKEN` تنظیم شده باشد، تصاویر در Vercel Blob با دسترسی عمومی ذخیره می‌شوند؛ در غیر این صورت در `public/uploads` نوشته می‌شوند.

برای استقرار، یک محیط اجرای Node.js و PostgreSQL لازم است. می‌توان از Vercel با دیتابیس ابری یا یک سرور Node.js با دیسک ماندگار استفاده کرد. در محیط‌هایی با فایل‌سیستم موقت مانند Vercel، برای ماندگاری آپلودها Blob را تنظیم کنید. GitHub محل نگهداری کد است؛ GitHub Pages اجرای API، احراز هویت و دیتابیس این پروژه را پشتیبانی نمی‌کند.

متغیرهای محیطی را روی میزبان تنظیم کنید، سپس مایگریشن‌ها و بیلد را اجرا کنید. برای سرور Node.js:

```bash
npm ci
npm run db:deploy
npm run build
npm run start
```

در Vercel مدیریت اجرای سرور توسط پلتفرم انجام می‌شود. Seed نمونه بخشی از راه‌اندازی محیط واقعی نیست. اتصال واقعی پرداخت باید پیش از پذیرش پرداخت آنلاین تکمیل و آزمایش شود.

| دستور | کاربرد |

آزمون اختیاری دیتابیس به `PAYMENT_TEST_DATABASE_URL` نیاز دارد که پارامتر `schema` آن باید نام تازه‌ای با قالب `katuni_payment_test_<id>` باشد؛ بخش id فقط ۸ تا ۳۲ حرف کوچک انگلیسی یا رقم است. آزمون از schema موجود یا عمومی استفاده نمی‌کند: schema تازه می‌سازد، مایگریشن‌ها و سناریوهای هم‌زمانی را اجرا می‌کند و فقط همان schema آزمایشی را پاک می‌کند. حساب دیتابیس باید مجوز ساخت schema داشته باشد. این آزمون پول واقعی منتقل نمی‌کند.

## نظرات، مشخصات و آمار بازدید

در فرم محصول، مشخصات کفش به‌صورت ردیف‌های نام و مقدار اضافه، ویرایش، حذف و مرتب می‌شوند. هر کاربر واردشده برای هر محصول یک امتیاز و نظر دارد. فقط موارد تأییدشده در امتیاز عمومی و مرتب‌سازی محبوب‌ترین حساب می‌شوند؛ ویرایش نظر، آن را دوباره به صف بررسی می‌فرستد. بررسی ادمین نسخهٔ نظر را کنترل می‌کند تا روی ویرایش تازه تصمیم قدیمی ثبت نشود. صفحهٔ بررسی در /admin/reviews است.

صفحهٔ /admin/analytics آمار را از زمان فعال شدن ثبت بازدید نشان می‌دهد. بازدید قابل‌شمارش یعنی نمایش یک صفحهٔ عمومی، با حداکثر یک ثبت برای همان مرورگر و مسیر در هر ۳۰ دقیقه. بازدیدکننده بر پایهٔ کوکی امضاشدهٔ HttpOnly تخمین زده می‌شود؛ مرورگرهای مختلف یا پاک کردن کوکی، بازدیدکنندهٔ جدا محسوب می‌شوند. نمودار روزانه از منطقهٔ زمانی تهران استفاده می‌کند. صفحات ادمین، حساب کاربری، تسویه و پرداخت، پیش‌واکشی‌ها و ربات‌های شناخته‌شده ثبت نمی‌شوند. هیچ آمار تاریخی ساختگی اضافه نمی‌شود.

IP گزارش‌شده فقط در پنل ادمین نمایش داده می‌شود و هویت قطعی کاربر نیست. پشت reverse proxy، باید هدرهای forwarding ورودی را خود proxy بازنویسی کند تا آدرس گزارش‌شده معتبر باشد. اطلاعات جست‌وجو و پارامترهای URL ثبت نمی‌شوند؛ ارجاع‌دهنده فقط به دامنه محدود است. کوکی بازدید از AUTH_SECRET استفاده می‌کند و مستقل از نشست ورود است.

آزمون‌های این بخش در npm test هستند. npm run test:product-engagement و npm run test:analytics آن‌ها را جدا اجرا می‌کنند. آزمون اختیاری npm run test:product-engagement:db مسیر ثبت، تأیید، ویرایش و برچسب خریدار را با PostgreSQL واقعی در یک تراکنش rollback‌شونده می‌سنجد و دادهٔ نمونه‌ای باقی نمی‌گذارد. این دستور برای بارگذاری .env به Node.js 20.9 یا بالاتر نیاز دارد.
